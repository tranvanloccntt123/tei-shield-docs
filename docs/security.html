Trust model and detector coverage

The device is an untrusted environment. A local negative result means only that this particular check did not observe its indicator. unsupported and error must never be converted to a trusted result. Checks produce code/status/confidence; they do not authorize server operations or terminate the app.

This version does not implement arbitrary PLT/GOT scanning, disassembly of all system functions, cross-process memory access, Magisk-hide bypasses, or direct machine-code syscalls. Inspecting a function's owner does not detect every inline hook. The checks cover the SDK's own text, not every binary in the host app. These limitations are explicit rather than represented as successful checks.

Selecting detectors​

The app requests detectors through ShieldCheck and AssessmentOptions; the native core receives exactly the bit mask of selected native checks. Selecting emulator on Android therefore does not read /proc, enumerate loaded images, inspect certificates, sensors, or battery. Unselected checks must not be interpreted as notDetected; they have no signal in the Assessment. See the integration guide for the appropriate API.

Native sensitive strings are XOR-obfuscated at compile time with volatile decode and short-lived buffers. This prevents basic strings inspection of selected detector constants, not determined reverse engineering. Exported symbol names, JSON keys, OS build-property markers and documentation strings remain readable. No private key or shared API secret is embedded. Android Keystore security level is reported locally and is not falsely treated as hardware key attestation; Play Integrity binds the public key but does not prove that this key is StrongBox-backed.

Binary sealing​

The final linked ELF64/Mach-O64 is hashed over its instruction section. A 64-byte reserved non-code record stores magic, little-endian virtual address, size and SHA-256. The build rejects ordinary relocations into the measured region. Runtime checks verify that the configured range lies inside a readable executable mapping before hashing. Unsealed builds report unsupported. CMake seals before ad-hoc signing on macOS; Xcode seals before framework signing. Strip preserves the measured bytes; artifact audit verifies that after packaging.

An attacker who patches the verifier and its expected digest can bypass local integrity. The embedded manifest is a local detection mechanism, not an independent root of trust. Google/Apple evidence is independently checked by the server. Source SPM builds do not run the seal step: use the generated binary package for release integrity checks.

Server policy​

Google verdicts must match request hash, package name, all current signing certificate digests, timestamp, PLAY_RECOGNIZED, MEETS_DEVICE_INTEGRITY and LICENSED. Permit old and new valid release digests during planned signing-key rotation; remove deprecated ones deliberately. Play App Signing certificates differ from upload-key certificates.

App Attest validation checks the Apple certificate chain through the pinned root in node-app-attest, certificate validity dates, nonce, key ID, credential ID, RP ID hash, zero enrollment counter and exact environment. Assertions validate signatures, RP ID and a strictly increasing counter. Development accepts development evidence only; production accepts production only. DeviceCheck is not silently substituted. The Apple verifier dependency is version-locked; review provider protocol/library changes before upgrades.

The sample has no mock-provider switch. Test fakes are confined to server/test/. Demo authentication is development-only. Production must supply a real Authenticate callback, stable user IDs, session IDs that change when sessions rotate, managed credentials, TLS, database access controls, and telemetry with redaction. Store never trusts a claimed hardware/security level from the client.
