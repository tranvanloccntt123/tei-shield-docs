TEI1 wire protocol

Transport uses HTTPS. Evidence is never placed in URL query strings. The sample routes accept bodies up to 65,536 bytes. Session authentication is required for every route; attestation does not authenticate the human user.

Canonical bytes​

TEI1 (4 ASCII bytes), followed by each field as uint32 big-endian UTF-8 byte length || UTF-8 bytes. Fields appear in fixed order. No delimiter escaping, Unicode normalization, URL decoding, query sorting, or JSON reserialization. Lowercase hexadecimal body SHA-256; timestamps are 13-digit Unix milliseconds. Golden vectors include multibyte UTF-8, NUL and empty fields.

Request fields:

request, METHOD, audience, raw-path-and-query, sha256(original-body-bytes), timestamp, challenge, keyId

Enrollment fields:

enroll, platform, audience, challenge, keyId, publicKey

Android publicKey is canonical padded Base64 SPKI DER for P-256. Android key ID is unpadded Base64url SHA-256 of that DER. iOS key ID is the exact padded Base64 string from App Attest; enrollment publicKey is empty because the server derives it from the attestation certificate. Session binding is supplied by the stored challenge, rather than caller-controlled claims.

Android signs canonical bytes with SHA256withECDSA, DER signature encoded as padded Base64. Both enrollment and protected requests require this proof of key possession. Play Integrity requestHash is unpadded Base64url SHA-256 of the same canonical bytes. iOS gives SHA-256 of canonical bytes to App Attest as clientDataHash. Server verification receives the original canonical bytes, not their hex representation.

Endpoints​

All routes require the application's session authorization. JSON request bodies for challenge/enrollment/revocation use UTF-8. The protected request body is opaque bytes, even when Content-Type is JSON.

EndpointInputOutput
POST /v1/challenges{"purpose":"enroll"} or {"purpose":"request"}{value, expiresAt, purpose}
POST /v1/devices{platform, challenge, keyId, publicKey, evidence, signature}{keyId}
POST /v1/sensitiveOriginal body and X-TEI-Proof header{id, status:"accepted"}
POST /v1/devices/revoke{keyId}{revoked:true}

X-TEI-Proof is padded Base64 of UTF-8 JSON:

{
  "platform": "android",
  "challenge": "<server-issued value>",
  "keyId": "<registered key>",
  "timestamp": "1788600000000",
  "evidence": "<Play Integrity token or base64 App Attest assertion>",
  "signature": "<base64 Android DER signature; empty for iOS>"
}

Enrollment evidence is a Play Integrity token or base64 App Attest attestation. iOS enrollment signature is empty. Proof JSON ordering is irrelevant: its fields reconstruct canonical bytes alongside actual HTTP method, actual raw URL, server-configured audience and actual body bytes.

Challenges are 32 random bytes encoded Base64url without padding, expire after 120 seconds, and are bound to user ID, session ID and purpose. Consumption, device counter update and the sample business operation commit in one PostgreSQL transaction. Failed verification rolls back all three. Expiry is rechecked after provider verification; duplicate enrollments never replace an existing or revoked key. A revoked key cannot be reactivated by enrolling it again.

The sensitive endpoint writes a sample operation record; it does not process payments. Put real database business effects inside the same transaction. For external side effects use a transactional outbox and downstream idempotency. Do not move a sensitive action after the transaction and assume it is exactly once.

Failure and retry​

Errors contain {error, retryable}. Missing authentication returns 401, malformed input 400, rejected verification 403, duplicate registration 409, rate limiting 429 and temporary provider failure 503. Provider exception text, bodies, tokens and signatures are not returned or logged.

After network uncertainty, fetch a fresh challenge and regenerate the proof. Google tokens may already have been decoded; iOS counters may have advanced. Never retry a consumed token indefinitely. The sample does not expose operation lookup: production integrations must supply an idempotency/operation-status flow if users need to recover the result of an accepted action whose response was lost.

Configure upstream header limits for Play Integrity proofs, preserve exact path/query bytes, disable redirects, and do not decompress or transform the signed body before verification. Requests on iOS should be sent serially per key: the SDK serializes assertion generation but cannot serialize the caller's network delivery. A later counter arriving first safely rejects an earlier assertion; retry that operation with a new challenge.
