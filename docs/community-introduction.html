TEI Shield: Local Device Risk Signals for Mobile Apps

Modern mobile applications increasingly protect sensitive actions: account recovery, high-value transactions, rewards, content access, and changes to security settings. In many of these flows, the app needs more context about the device it is running on.

That is the problem TEI Shield is designed to help with.

TEI Shield is an open-source, native security SDK for Android and iOS. It collects a focused set of local device-risk signals and returns them in a small, consistent assessment model. Applications can use those signals to inform their own risk policy—for example, asking for step-up verification, sending an event for review, or applying a stricter flow to a sensitive action.

The project is built around a simple principle: device-local signals are useful context, but they are not a trust anchor.

What TEI Shield checks​

TEI Shield exposes independently selectable detectors, including:

  • debugger presence;
  • injected or unexpected native images;
  • writable system mounts and privileged-file indicators on supported platforms;
  • selected native function and pointer checks;
  • the integrity of TEI Shield's own executable text;
  • emulator or simulator indicators;
  • Android application identity, when explicitly configured; and
  • hardware and environment signals such as missing motion sensors or unavailable battery information.

The exact coverage depends on the platform and build type. Unsupported checks are reported explicitly instead of being presented as successful checks. This distinction matters when an app is deciding how much confidence to place in an assessment.

Every result follows the same shape:

{
  "schemaVersion": 1,
  "signals": [
    {"code": "emulator", "status": "notDetected", "confidence": "high"}
  ],
  "durationMs": 1.4
}

The status can be detected, notDetected, unsupported, or error. A notDetected result means that a particular detector did not observe its indicator; it does not prove that the device is clean. Likewise, unsupported and error should never be converted into a trusted result.

Local-first by design​

The current SDK performs assessment on the device. It does not require an account, call a TEI Shield backend, send telemetry, or upload evidence. The host application owns the resulting policy and decides what to do next.

This makes the SDK useful in places where teams want a small, predictable integration surface. An app can run a single check without creating a long-lived SDK instance:

val signal = TeiShield.check(applicationContext, ShieldCheck.EMULATOR)
let signal = await TeiShield.check(.emulator)

For longer-lived flows, an app can select several detectors and choose whether assessments run at initialization, on demand, or when the app returns to the foreground. Unselected checks are not run and must not be interpreted as notDetected.

One core, several integration paths​

TEI Shield keeps the core detection and serialization logic in C++, then exposes platform-native APIs on top of it:

  • Android: Kotlin API with JNI, distributed through Maven Central;
  • iOS: Swift concurrency API backed by an XCFramework;
  • React Native and Expo: TypeScript API through an Expo native module; and
  • Flutter: Dart API through a thin platform bridge.

The adapters share the same assessment vocabulary, so a cross-platform product can keep its application policy consistent while still using platform-specific detectors where they are available.

The minimum native targets are Android API 26 (Android 8) and iOS 15. React Native/Expo and Flutter packages are available through their usual package registries. See the getting started guide for installation details and platform-specific examples.

Security without overclaiming​

Security tooling is most useful when its boundaries are clear. TEI Shield does not promise to detect every rooted, jailbroken, instrumented, emulated, or modified device. It does not replace server-side authentication, authorization, provider attestation, or transaction controls. An attacker who controls the client may be able to bypass local checks, including the local code-integrity verifier.

That is why TEI Shield treats its output as advisory risk context. A sensible policy might look like this:

error / unsupported  -> record the state; use fallback or step-up
detected             -> require additional verification for sensitive actions
notDetected          -> continue the normal business policy

The right response depends on the product. A financial action, a game reward, and a low-risk content view should not necessarily use the same threshold. TEI Shield gives the app explicit signals so the product team can make that decision deliberately.

Why we are sharing it​

Device-risk detection sits at the intersection of mobile engineering, reverse engineering, privacy, and product policy. It benefits from review by people who have encountered different operating-system versions, instrumentation tools, packaging pipelines, and false-positive patterns.

The project is released under the MIT License. We welcome:

  • issue reports with reproducible device and build details;
  • review of detector coverage and platform assumptions;
  • improvements to Android, iOS, React Native, and Flutter integrations;
  • tests on clean devices and controlled rooted or jailbroken lab devices; and
  • documentation improvements, especially around interpreting unsupported, error, and low-confidence signals.

If you are evaluating TEI Shield, start with the integration documentation, read the trust model and detector coverage, and treat the assessment as one input into a broader security design.

TEI Shield is intentionally modest in what it claims: small native checks, explicit results, local execution, and clear limits. That makes it a practical foundation for applications that need more device context without turning a client-side signal into a false promise of trust.
