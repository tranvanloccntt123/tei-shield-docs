Troubleshooting and integration checks

First identify the failure layer: package/build, call-level exception, or a returned signal. status: "error" inside a successful assessment is different from a rejected Promise/Future or a native exception. Record platform, installed SDK/wrapper version, build variant, selected codes, and redacted error code before changing configuration.

Commands for inspecting an Android host from its native directory:

./gradlew :app:dependencies --configuration releaseRuntimeClasspath
unzip -l app/build/outputs/apk/release/app-release.apk
apksigner verify --print-certs app/build/outputs/apk/release/app-release.apk

Adapt module, variant, and artifact paths to the app. For the SDK repository sample, the module is sample, not app.

Verify an integration before release​

  1. Run an empty selection and confirm zero signals; run emulator only and confirm exactly that code.
  2. Run your intended selection on a real device and emulator/simulator. Check every status and missing code, not just Promise/Future success.
  3. For Android identity, use the actual release signer and deliberately test a mismatched allowlist in a controlled test build.
  4. Verify the sealed release artifact and exercise release/R8 builds, not only debug builds.
  5. Exercise initialize, foreground, manual override, teardown, and recreate. Handle pending manual calls during close.
  6. Confirm no local result directly authorizes a backend operation; test app policy for empty, unsupported, error, detected, and unknown schema cases.

These are integration checks to run, not claims that physical-device acceptance has passed. See the verification record for historical evidence and its limits. For an issue report, include reproduction steps and redacted diagnostics; omit user data, credentials, keys, and tokens.
